# HY2 UDP 乱序恢复与数据报编号（UDP Reorder）

[返回功能目录](../features.md)

HY2 服务端按客户端的包序号，恢复同一 UDP 会话内被网络调换的上行数据报；同时给自己发出的数据报按会话递增编号，使对端能对下行做同样的恢复。面向游戏等会把迟到的旧包计为丢包的 UDP 应用。

QUIC 给自己的每个包编号，但 RFC 9221 的 DATAGRAM 帧按到达顺序交付，顺序不被还原，所以链路乱序原样穿透到它承载的 UDP。HY2 消息自己的包序号是唯一能把顺序还原回来的依据。

## 上行恢复

没有配置开关。hysteria 入站为客户端打开的每个 UDP 会话自动启用；Xray 作为 HY2 客户端时不处理上行。

只对按会话连续编号的客户端生效。sing-quic 系客户端（如 mihomo）与本分支的 Xray 客户端每条消息的包序号递增，同一消息的分片共用序号。会话要先连续出现递增序号才会暂存数据报；包序号恒为 0 或分片随机取值的客户端（官方客户端、未升级的 Xray）照常直通。

- 按序到达的数据报立即交付，不增加延迟。
- 序号出现不超过 32 的缺口时，先到的数据报最多暂存 2 ms，缺口补上即按序交付；超时则放弃缺口按序放行，之后迟到的包直接交付。
- 缺口超过 32 视为丢包过多或计数重置，立即交付并重新确认连续性；单会话最多暂存 64 个数据报。
- sing-quic 以 65535 取模计数、不发送 0xFFFF，跨越回卷不算缺口。

## 下行编号

`UDPWriter` 原本给每条未分片的消息写 `PacketID: 0`，分片时才随机取一个值，对端因此没有任何排序依据。现在按会话递增编号：以 65535 取模、从 1 开始、不发送 0xFFFF，与 sing-quic 一致；分片仍共用所属消息的序号。

服务端与客户端两侧的写入器共用这段逻辑，所以 Xray 作为客户端时上行也带序号，对端若实现了恢复即可生效。字段长度固定 2 字节，改变取值不影响包长与时序；它位于 QUIC DATAGRAM 载荷内部，只有已认证的对端能看见。

本端不恢复下行顺序——那是客户端的事，mihomo 侧见
[HY2 下行 UDP 乱序恢复](https://github.com/qwqgong-ui/mmmmmmhhhmmm/blob/dev/docs/features/hy2-downlink-reorder.md)。

## 实测依据

2026-09-17 战争雷霆经 mihomo 连接：上行 8.4% 的数据报在国内至东京的线路上被调换，调换的相邻包到达服务器网卡时最多相差 0.11 ms，mihomo 与 Xray 自身未打乱顺序。

2026-09-20 用裸 UDP 复测下行：东京与洛杉矶两台服务器发往同一客户端，每 1500–2000 个包有 76–294 次乱序，倒置距离几乎全为 1；而这两台**互发**时 1500/1500 零丢包零乱序。乱序只在包间距小于约 100 µs 时出现，且在客户端网卡抓包时就已存在。成因是客户端侧接入网络对背靠背包的处理，与 GSO 无关——关闭 GSO 只是降低了包背靠背的频率。
